## 1. Direction

Build a small inventory app around three actions: find something, correct what is on the shelf, and record a purchase. Prove that these actions are easy enough to maintain a trustworthy inventory before adding barcode lookup.

The confirmed delivery model is a progressive web app (PWA) served by GitHub Pages at `https://cupboardcache.sciomedes.com/`. The user visits it once online and uses the browser's Add to Home Screen or Install action. A service worker caches the application so it can subsequently launch and work offline. The inventory saves automatically in browser storage on the device; JSON files are used for manual export and import. GitHub serves application files and updates, while inventory processing and storage stay on the device.

There is one working inventory, with no account, login, application backend, or synchronization. Use the installed app as the normal working copy. A full container is one unit, so 2.5 jars is valid even in qualitative display mode. Repository: public `rduncangt/CupboardCache`. Richard owns `sciomedes.com` and has configured the CNAME for deployment.

Preserve the brief's UUIDs, record timestamps, soft deletes, single persistence layer, sticky resupply flags, manual backups, and bounded history. Keep the full dataset in memory and scan it directly for searching, filtering, and sorting. The exclusions in the brief remain in force; barcode lookup belongs after v1.

The details below are implementation recommendations where the brief did not specify behavior. Outstanding product choices are collected in section 7. The first technical milestone proves installation, offline relaunch, and local persistence on the actual phone; these capabilities have not yet been tested for this app.

## 2. Stack, installation, and local storage

### Recommended stack

| Part | Recommendation | Reason and tradeoff |
| --- | --- | --- |
| UI | TypeScript, Preact, ordinary CSS | Components keep forms and derived views consistent. Preact adds a small runtime dependency; plain TypeScript is also viable but requires more manual UI state handling. |

| Verification | Type checking, Vitest for domain rules, a few Playwright browser tests | Concentrate tests on inventory correctness, offline operation, update safety, and recovery. Installation and backup export/import also need a real-phone check. |

## 3. Concrete data model

These records are implemented inside one inventory document in IndexedDB and exported in the same preferred JSON shape. Nested value objects such as package size do not need separate IDs. The runtime schema is in `src/model.ts`.

```ts
type UUID = string;
type Timestamp = string; // UTC ISO 8601
type LocalDate = string; // YYYY-MM-DD, without timezone conversion

interface RecordMeta {
  id: UUID;
  created_at: Timestamp;
  updated_at: Timestamp;
  deleted_at: Timestamp | null;
}

interface PackageSize {
  amount: number; // strictly positive; amount in ONE inventory unit
  unit: "g" | "kg" | "ml" | "l";
}

interface Item extends RecordMeta {
  name: string;
  notes: string;
  aliases: string[];
  category: string | null;
  location: string | null;
  quantity: number; // finite, nonnegative, in this item's unit
  unit: string;     // e.g. bag, stick, jar, g
  package_size: PackageSize | null;
  display_mode: "number" | "ladder";
  expiry: LocalDate | null;
  threshold: number | null;
  flagged: boolean;
  flag_source: string | null;
  flagged_at: Timestamp | null;
  restock_amount: number;
  barcodes: string[];
  never_prompt: boolean;
  verified_at: Timestamp | null;
  merged_into: UUID | null;
}

interface QuantitySnapshot {
  quantity: number;
  unit: string;
  package_size: PackageSize | null;
}

interface QuantityEvent extends RecordMeta {
  item_id: UUID;
  reason: "initial" | "adjust" | "recount" | "purchase"
        | "unit_change" | "merge" | "undo" | "use" | "add";
  before: QuantitySnapshot | null; // null for initial creation
  after: QuantitySnapshot;
  related_item_id: UUID | null;    // merge source, when applicable
  undo_of_event_id: UUID | null;
  note: string | null;
}

interface ShoppingExtra extends RecordMeta {
  text: string;
  completed_at: Timestamp | null;
}

interface Settings extends RecordMeta {
  retention_days: number; // default: 365
  last_export_at: Timestamp | null;
  writes_since_export: number;
  device_label: string;
  last_trip_ended_at: Timestamp | null;
  declared_locations: string[];
}

interface InventoryData extends RecordMeta {
  app: "ambry"; // preferred file-format identifier, not an app rebrand
  schema_version: 1;
  exported_at: Timestamp | null;
  device_label: string;
  counts: { items: number; events: number; extras: number };
  revision: number; // increment on commits; stale-edit check, not a record ID
  items: Item[];
  events: QuantityEvent[];
  extras: ShoppingExtra[];
  settings: Settings;
}
```

### Model boundaries

- An item represents one kind of stock counted in one consistent unit. Multiple containers are included in its quantity. Prefer one row per stock type; use short notes for distinctions that matter when shopping.
- Category and location are normalized text values with suggestions from existing items. Dedicated category/location records and management screens are unnecessary for v1.
- One item has one location and one expiry summary. Recommend that expiry mean **earliest known expiry among stock on hand**, and location mean the usual storage place. Multiple batches or independently counted locations require a later model change; see section 7.
- Item quantity is authoritative. History explains changes and can expire without changing current quantity. It is not an event-sourced database or the future sync queue.
- The shopping view is derived from active items with `flagged === true`, plus active, unfinished `ShoppingExtra` records. Typed extras must themselves be stored; the combined shopping list is not a separate entity.
- UUIDs and original timestamps survive import. Normal edits keep the record ID and `created_at`, update `updated_at`, and set `deleted_at` on deletion. Deleted items, aliases, flags, and retained history are included in backups.
- New items require a name, quantity, and unit. Defaults are `number` display, `count` as the unit, restock amount 1, empty notes/aliases/barcodes, no threshold or flag, and prompting allowed. The inventory document and singleton settings record have their own UUIDs and timestamps; their `deleted_at` stays null.

### Central write contract

`UI action → validate command → compute next state → commit IndexedDB transaction → refresh UI`

Commands include `createItem`, `editItem`, `adjustQuantity`, `setActual`, `recordPurchase`, `setResupplyFlag`, `deleteItem`, `restoreItem`, `mergeItems`, and shopping-extra changes. Settings, retention, migrations, and imports also use this boundary. UI components never write storage directly.

Read the latest document and apply its item changes, flags, timestamps, and events inside one read/write transaction, then publish the committed state to the UI. Queue commands within the app; a failed transaction leaves the prior stored state intact and keeps the user's attempted input available to retry. Report success only after transaction completion. Use the document revision to reject stale edits if another open tab has committed; refresh the in-memory view after a commit or when returning to the app. This is local consistency, not multi-device sync. The `idb` wrapper exposes transaction completion through `tx.done`. [idb transaction guidance](https://github.com/jakearchibald/idb#idbtransaction-enhancements)

Validate at both command and import boundaries: nonempty names and units; finite, nonnegative quantities and thresholds; positive package sizes; valid dates and UUIDs; unique IDs; valid record references; and supported file versions. Event-to-item references must resolve, including to tombstones. An optional `undo_of_event_id` may identify an event removed by retention; show “earlier event expired” rather than rejecting that otherwise valid file. Normalize arithmetic to six decimal places, use the same precision for threshold comparisons, and never display a small positive quantity as “out.”

## 4. Behavior that protects inventory quality

### Fast entry and reconciliation

The inventory screen opens with search prominent. Search matches name, aliases, and notes, ignoring case and word order for multiword queries. Scan the full item list; no index is needed. Keep zero-quantity items searchable and clearly labeled “out.” Deleted items appear only in a restore view or an explicit duplicate suggestion.

Each row offers a quick quantity adjustment and **Set actual**. The latter records an absolute count, updates `verified_at`, and logs a recount if the quantity changed. A metadata edit or purchase must not pretend that the shelf was physically checked.

Provide both reconciliation approaches:

- **Immediate correction:** tap quantity, enter the actual amount, save, and continue. Show Undo for the last action.
- **Walk the shelf:** filter by location, then step through items with Confirm, Set actual, Out, and Skip. Confirm updates `verified_at` even when quantity is unchanged. Derive progress from the current walk and timestamps; a persistent reconciliation-session subsystem is unnecessary.

Use a “least recently checked” sort and the last-checked date to expose possible drift without claiming that age proves an item is wrong. Record a correction as a recount, not a purchase, so resupply stickiness survives.

### Quantities, spare containers, and units

Qualitative mode never stores another quantity or container count. Derive spares and the current container's fill from the same number. For positive `q`, use `spares = max(ceil(q) - 1, 0)` and `fill = q - spares`. For zero, both are zero.

This is a representation of total stock: two half-full jars equal one unit. It does not preserve individual container identities or distinguish several partly used containers.

Examples: 2.5 jars displays “2 full + half”; 2 jars displays “2 full”; 0 displays “out.” Proposed display bands for the current container are low for `0 < fill <= 0.35`, half for `0.35 < fill <= 0.75`, and full above 0.75. These are approximate labels; the number remains inspectable and switching display mode never rounds it.

Quick controls labeled **Set open container** write `spares + 1`, `spares + 0.5`, `spares + 0.2`, or `spares + 0`. Thus marking the open jar out at 2.5 leaves 2. Provide a separate **All out** action for total quantity zero, and **Add full container** for an increase of one. A resupply purchase uses the distinct Bought action described below.

Package conversion is explicit: flour with unit `bag` and package size `{ amount: 1, unit: "kg" }` converts 432 g to 0.432 bags. Retain that one quantity; the precise display is calculated from it. Support g↔kg and ml↔l plus the item's package mapping. Custom count units remain distinct, and mass never converts to volume without information the app does not have.

For edits over time:

- Correcting a unit label's spelling leaves its meaning and quantity unchanged.
- Changing the measurement unit requires an explicit conversion factor and a preview. Convert quantity and threshold together, update or remove the package mapping consistently, and record a unit-change event. This representation change must not trigger resupply.
- Never silently redefine a nonempty “bag” by changing its package size. Recommend allowing a new package size at zero stock; otherwise reconcile into a stable unit such as grams, or keep differently sized stock as an explicitly named variant. Review the threshold when changing packaging.
- Historical events retain their original unit and package snapshots. A later edit cannot reinterpret an older event's amounts.

### Resupply state transitions

The following are proposed exact semantics for the brief's sticky flag model. A threshold of zero is valid; `null` disables automatic threshold monitoring. “At threshold” means `quantity <= threshold`.

| Action | Quantity | Resupply flag |
| --- | --- | --- |
| Normal change crosses from above threshold to at/below it | Apply change | Raise, unless `never_prompt` is enabled |
| Recount raises quantity | Set actual | Preserve the flag |
| Create an item already at/below its threshold | Initial quantity | Raise unless never-prompt |
| Set/change a threshold, or re-enable prompting, while already low | Unchanged | Raise unless never-prompt |
| Manually add to shopping | Unchanged | Raise, including for a never-prompt item |
| Enable never-prompt or remove the threshold | Unchanged | Preserve existing flag; suppress future automatic prompting |
| Bought, with a positive amount | Add the purchased amount | Clear in the same action; offer “keep on list” for a partial purchase |
| Explicitly cancel a shopping need | Unchanged | Clear; this is a deliberate correction, not an automatic consequence of quantity |
| Delete item | Preserve data in tombstone | Hide item from active views |
| Undo last action | Restore affected state | Restore the prior flag along with the quantity |

Do not run threshold logic on render, search, file opening, or import. Otherwise a canceled need or a purchase could immediately reappear. After a flag is cleared while quantity is still low, crossing-only behavior will not raise it again until it rises above the threshold and crosses back down, or prompting settings change. Show that condition when recording a partial purchase and offer “keep on list.”

**Bought** is one action that updates stock and clears its shopping flag. Checking an ad-hoc entry completes only that entry; it does not create inventory automatically. Undo of a quantity change adds a compensating event rather than deleting the original event. Limit Undo to the latest action in the current session for v1.

### Duplicates and near duplicates

Prevent duplicates at entry: show existing matches while typing, including out-of-stock items. Normalize case, spaces, and punctuation, and compare word tokens so “Canned tomatoes” and “Tomatoes, canned” are candidates. Offer Use existing, Restore deleted, or Create distinct. Suggestions must not automatically merge different products.

Provide a small, deliberate merge flow for mistakes that slip through:

1. Choose the surviving item and add the other name to its aliases.
2. Review unit, location, expiry, threshold, and never-prompt conflicts explicitly.
3. Enter the actual combined quantity. Do not automatically sum: both rows may describe the same cans.
4. Preserve an existing shopping need by default using either item's flag.
5. Update the survivor, log its quantity change, and soft-delete the source with `merged_into` pointing to the survivor, all in one command.

Keep the source's history attached to its original ID and make it reachable from the survivor. Undo restores both items. A merged source is not offered as an ordinary independent restore without addressing the survivor's quantity.

### Backup, import, and history

Use the same versioned schema for the stored inventory and dated JSON backups. Normal edits save automatically in IndexedDB; **Export backup** serializes a committed snapshot to a separate file. Exported data stays on the device unless the user chooses to copy it elsewhere. A backup kept solely on the same device cannot protect against losing that device. Choose a manual backup habit, such as exporting after the weekly shelf check and copying that file somewhere safe.

Use a standard file input for import and a JSON download for export; add a native share action only if it helps on the actual phone. A download request alone cannot confirm that the file reached disk, so label it accurately and verify recovery by reopening an exported file during M1. [MDN download behavior](https://developer.mozilla.org/en-US/docs/Web/API/HTMLAnchorElement/download)

Import is a full replacement, not a merge or synchronization feature. Parse and validate the entire candidate in memory, show item/history counts and its update date, offer to export the current data, then ask for an explicit restore. Replace the document in one transaction. Invalid files leave current state untouched. Preserve record UUIDs, timestamps, tombstones, flags, quantities, settings, and retained history; assign a fresh local commit revision so a restore cannot revive an old tab's revision. Do not generate purchases or re-evaluate thresholds during import. Compact Ambry events (`at`, `kind`, `qty_before`, `qty_after`, `unit`, optional `unit_before`/`note`) are converted on import without losing history; see [data-format compatibility](DATA_FORMAT.md#compact-history-compatibility).

Keep the previous stored document intact while preparing a migration or replacement. Migrate supported older schemas on a copy, validate the result, and commit only after success. Reject unknown newer versions with an understandable message. If application code is too old for the stored schema, preserve the data and require a compatible app version. Never recover a parsing, migration, or storage failure by silently creating an empty inventory.

Recommend 365 days of history by default, configurable to a positive number of days. Run retention after loading the inventory and after a retention-setting change, then commit it through the persistence layer. Preview the number of events affected before shortening retention. Existing backup files remain unchanged.

**Explicit exception proposed to blanket soft deletion:** physically remove quantity events older than the chosen retention window. Merely marking them deleted does not bound storage. Keep soft-deleted operational records, including items and shopping extras. Expiring history never changes quantity, flags, last-checked timestamps, or deletion records. This exception needs a decision before implementing retention.

### Acceptance criteria for v1

- Answer ten representative “do I have this?” searches in under three seconds each on the actual phone, including home-screen launch trials while offline. Measure warm search and cold launch separately so startup cost stays visible.
- Update 15 familiar purchased items in under two minutes as an initial usability target, including confirmed automatic saves. Adjust based on observed use, while keeping the brief's five-minute friction failure in view.
- Walk a shelf, correct a quantity, confirm an unchanged item, and fix a duplicate without opening a long edit form for each item.
- Use 1,000 sample items plus a realistic year of events to check search responsiveness, startup, transaction time, and backup export/import. Measure history as well as item data; no pagination or index is planned.
- Round-trip a file containing fractional quantities, unit changes, manual flags, never-prompt items, completed extras, and deleted records. Invalid/newer-version files must not damage the current inventory.
- Verify equality at the threshold, sticky flags after recount, initial-low items, canceled needs, partial purchases, and Undo. Verify that import and unit conversion do not spuriously raise flags.
- Close and reopen after a successful save, simulate a failed transaction, and cancel an export or import. Check that a stale open tab cannot overwrite a newer committed inventory. Confirm that importing or updating the app preserves data on failure.
- After the initial online visit and installation, relaunch and operate entirely without network access. Test the production deployment and its service worker, not only the development server. Check touch controls, keyboard navigation, focus handling, and text labels for quantities and flags.
- Deploy a new version while the app is open, postpone its update, finish an edit, and then update. Verify the data and offline cache remain usable. Also test a failed update download and restore from a backup after deliberately clearing test storage.
- After two shopping cycles, physically check 30 representative items. Proposed gate: every in-stock/out-of-stock answer is correct and at least 28 quantities match the chosen granularity. Repeat after correcting any workflow problem; do not respond to drift by adding unrelated features.

## 6. Where I disagree or would qualify the brief

**Home-screen installation needs offline caching and a backup policy.** Adding an icon alone does not guarantee offline operation or permanent data retention. Build and test the service worker, IndexedDB persistence, and manual recovery in the first milestones. Everyday use then avoids file selection and explicit saves.

**The item-size estimate is not the whole file-size estimate.** UUIDs, metadata, aliases, deleted records, and a year of history add data. For illustration, 20 events a day at 400 bytes each already contribute about 2.9 MB a year before the inventory itself. This is still small enough for the proposed approach; it changes what we measure, not the need for infrastructure.

**A sticky flag needs an explicit cancel action.** “Only clear when bought” otherwise makes an accidental manual flag or a canceled plan awkward to fix. Preserve stickiness against quantity changes, while allowing deliberate cancellation without inventing a purchase.

**A single expiry and location cannot describe every container.** The proposed earliest-expiry/usual-location convention is an approximation. If independently tracking multiple locations or expiry batches is essential, decide that before implementing the item editor; a silent approximation would undermine trust.

**Retained tombstones and bounded history serve different purposes.** Keep soft deletion for operational records and allow explicit retention to remove expired events. The event log is disposable history, not future synchronization infrastructure.

The basic scope, one quantity, independent resupply state, simple in-memory search, and early backup requirement are sound. Barcode lookup should wait until the manual workflow survives the pilot. Its later feasibility work must include camera support, lookup coverage, provider terms, and cross-origin API access from the hosted app; cache only personally scanned products and preserve manual entry.
